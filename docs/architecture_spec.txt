1. Purpose and status
This document defines the proposed target architecture and system design for a configurable financial-risk platform intended to
replace selected Moody’s calculation and balance-sheet risk capabilities. It complements the Detailed Data Model and the
synchronized frontend/backend workstream plans.

Status: working design baseline, not a production-approved architecture. Client infrastructure, exact Moody’s modules in scope,
source feed contracts, regulatory jurisdictions, non-functional targets, hosting constraints and security policies require confirmation.
  MVP principle: broad platform architecture, deliberately bounded initial implementation. Build durable control points and
  extension contracts; limit initial volumes, integrations, instrument coverage and calculation depth until validated
  requirements and benchmark data are available.


2. Design objectives and principles
 • Replace the calculation capability that the client actually uses, not reproduce proprietary internals or assume every Moody’s module is
   licensed.

 • Separate source payloads, canonical financial data, configurable rules and deterministic calculation services.

 • Treat financial data quality, lineage, security, auditability and controlled change as first-class platform capabilities.

 • Accept uncertain source shapes through registered contracts, profiling and versioned mappings. Never silently drop or reinterpret
   unknown fields.

 • Make each calculation reproducible from pinned input snapshots and exact versions of schema, mappings, instruments, rules,
   assumptions and engine.

 • Keep AI outside the authoritative calculation path. AI may explain, retrieve, propose or orchestrate approved actions, with permissions
   and human approval.

 • Use modular boundaries and versioned APIs so ALM/IRRBB, collateral and capital modules can be added without rewriting ingestion
   or orchestration.

 • Reference implementation: React/TypeScript frontend and a typed backend API (FastAPI is a reasonable Python-oriented option for
   data and calculation workloads); final framework must match the team and client environment.

 • Use a relational database for configuration, identity references, metadata, canonical entities, run manifests and results. Use object

   queue may be sufficient for the MVP; preserve an adapter boundary for a dedicated broker later.

 • Keep the deployment cloud-neutral until client hosting and security requirements are confirmed. Avoid committing to a specific vendor
   from this draft alone.


6. Core runtime flows
6.1 Ingestion and schema-change flow
 1. Register source system/profile and a provisional or approved source contract.

 2. Upload or receive a file/feed; create an import job and immutable artifact reference, hash, timestamps and uploader/source identity.

 3. Profile columns, types, null rates, distinct values and value distributions. Unknown fields are retained in the raw artifact and surfaced
   as candidates.

 4. Apply an explicit, versioned source-to-canonical mapping. Mapping validation checks required fields, conversions, units, date
   semantics and key uniqueness.

 5. Run data-quality rules. Accepted records enter a versioned canonical dataset snapshot; invalid records are rejected or quarantined
   with actionable issue codes.

 6. Run source-to-target reconciliation where totals/counts are meaningful. Record all warnings and approvals.

 7. If drift is detected, create a review/change proposal. Do not auto-promote schema, mapping or rule changes into production.


                                Financial Risk Platform | Architecture & System Design | Working Draft v0.1 • Page 3
6.2 Calculation and result flow
 1. User selects dataset snapshot, calculation module/version, reporting date, rule-set version, assumption set and scenario.

 2. API authorizes access and validates that required inputs and approved configuration versions exist.

 3. Orchestrator creates a run record and immutable run manifest; the job moves through queued, running, validation, completed/failed
   states.

 4. Calculation service executes deterministic, unit-tested logic against a stable input snapshot. It records intermediate values, warnings
   and lineage references.

 5. Post-run checks validate invariants, totals, expected row counts and reconciliation tolerances. A failed control marks the run as failed
   or requiring review, never silently successful.

 6. Persist results and manifest; present metrics, warnings, source-to-result lineage and comparison to benchmark/baseline.

 7. Any rerun after changing input or configuration creates a new run. Do not overwrite historic results.

6.3 Governed AI workflow
 1. User asks for an explanation, impact assessment or a proposed configuration change.

 2. AI gateway checks identity, scope, data classification, approved model route and permitted tools.

 3. Retrieval is limited to authorized records/documents; references are stored with the AI request.

 4. AI returns a grounded explanation or a structured proposal, with uncertainty and evidence links.

 5. Proposal is validated by deterministic services and routed for human approval where consequential.

 6. Only approved actions are executed through allowlisted APIs. Tool calls, inputs/outputs metadata, approvals and evaluation results
   are audited.

8. Canonical financial domain and data boundaries
 • Raw zone: original source artifacts and immutable metadata. Restrict access; apply retention and encryption policies.




                                Financial Risk Platform | Architecture & System Design | Working Draft v0.1 • Page 4
 • Staging zone: parsed source rows with source record identifiers, import batch, raw-field map and parsing status.

 • Canonical zone: normalized entities with internal stable IDs, source identifiers, validity/effective dates, version and provenance.

 • Configuration zone: schema/mapping/rule/assumption/module versions and approval history.

 • Calculation zone: run manifests, input references, intermediate values, result records, warnings and lineage edges.

 • Presentation zone: report instances and views derived from authorized results; reports carry run ID and configuration versions.

 • AI evidence zone: request metadata, retrieval references, tool-call metadata, proposals, approvals and evaluation outcomes. Avoid
   duplicating raw sensitive content unless explicitly approved.

For financial values, use fixed-precision decimal types and explicit currency/unit fields. Preserve source precision and define rounding
points per approved calculation specification. Store dates, timestamps, time zones, business dates and effective dates distinctly.

10. Security, privacy and governance

                                Financial Risk Platform | Architecture & System Design | Working Draft v0.1 • Page 5
 • Authentication: enterprise identity provider using OIDC/OAuth2 where available; do not invent a parallel identity store unless required.

 • Authorization: RBAC with data-scope constraints; enforce tenant/entity/dataset permissions on the server and at query boundaries.

 • Least privilege: separate roles for platform admin, data steward, risk analyst, approver, auditor and service identity; final role model
   requires client approval.

 • Encryption: TLS in transit; database, object storage, backups and secrets encrypted at rest using approved key management.

 • Secrets: managed secret store or equivalent; no credentials in source control, frontend bundles, logs or documents.

 • Audit: record actor/service, action, object, timestamp, correlation ID, outcome, approval reference and version identifiers. Protect audit
   records against ordinary modification.

 • Data minimization: mask or redact raw values in logs and UI where unnecessary; restrict raw artifacts and quarantined records.

 • Change governance: maker-checker approval for production schema, mapping, rule, assumption and module configuration changes
   where required.

 • AI controls: approved model routing, prompt/data classification, retrieval access checks, tool allowlist, prompt-injection defenses,
   output validation, human approval and retention controls.

 • Operational security: dependency scanning, static analysis, secret scanning, vulnerability remediation, penetration testing and incident
   response.

No jurisdiction-specific compliance claim is made here. Data residency, retention, privacy, encryption key ownership,
segregation-of-duties and regulatory evidence requirements must be confirmed with the client.

12. Calculation correctness and reproducibility
 • Every run has a unique ID and immutable manifest including reporting date, source dataset snapshot, schema version, mapping
   version, instrument model/version, rule-set version, assumptions, scenario, module version, engine build, calculation parameters and
   user/service identity.

 • Store explicit references to input records and source artifacts; maintain lineage from result to intermediate value to canonical input to
   source record.

 • Use deterministic calculation code with fixed-precision arithmetic, explicit rounding rules, stable ordering where relevant and controlled
   random seeds for any approved stochastic method.

 • Maintain golden datasets and independently approved expected outputs for each financial module and supported instrument type.

 • Run unit tests, property/invariant tests, regression tests, reconciliation tests and parallel comparisons against the incumbent system
   where permitted.

 • Define tolerances per metric and explain whether a comparison is exact, rounded, or tolerance-based.




                                Financial Risk Platform | Architecture & System Design | Working Draft v0.1 • Page 6
 • Never label a module production-ready until domain experts approve formulas, coverage, edge cases, regulatory interpretation and
   reconciliation evidence.


13. AI and agentic design guardrails
 • AI is an optional application layer, not a dependency of the deterministic financial calculation path.

 • Use retrieval augmented with authorized source documents, rule definitions, model documentation and run evidence; cite the evidence
   in explanations.

 • Agent tools are explicit allowlisted APIs with typed inputs, scoped permissions, timeouts and auditable outputs.

 • AI-generated mappings, rules or assumptions are proposals. They require validation and approval before promotion.

 • Do not let an agent execute arbitrary SQL, modify historical run results, change permissions, or approve its own proposal.

 • Evaluate AI for groundedness, correctness, leakage, refusal/permission behavior, tool safety and regression; store evaluation version
   and outcomes.

 • External model APIs are optional and must be approved for data residency, contractual terms, privacy and retention. The core product
   must function when AI is disabled.

17. Testing strategy and release gates
 • Unit: parser edge cases, mapping conversions, financial functions, rounding, rule evaluation and state transitions.

 • Contract: OpenAPI request/response schemas, error envelopes, pagination and idempotency.

 • Integration: source artifact through canonical data, calculation, result persistence, lineage and report.

 • Security: authorization matrix, data-scope isolation, permission revocation, audit integrity, upload limits and injection defenses.

 • Data quality: nulls, duplicates, invalid dates, unit/currency mismatch, missing references, outliers and unknown columns.

 • Financial regression: approved golden cases, boundary cases, negative/zero values, maturity cutoffs, day-count conventions and
   supported instrument types.

 • Reconciliation: source-to-canonical counts/totals and incumbent-vs-new results with metric-specific tolerances.

 • AI evaluation: grounded citations, unauthorized retrieval attempts, unsafe tool requests, proposal validation and regression.

 • Operational: retry, restart, partial failure, backup/restore, load and concurrency tests.

Release gates: no production calculation sign-off without named financial owner, approved calculation specification, golden dataset,
tolerance policy, defect disposition, lineage evidence and documented rollback.

20. Definition of done for the first end-to-end slice
• A user with the correct role can register a source, import a sample dataset and inspect a data profile.

• Unknown columns are retained in the source artifact and visibly flagged for review.

• A versioned mapping can be validated and used to create canonical records; invalid rows are quarantined with clear issue codes.

• Approved configuration versions are pinned to a calculation run manifest.

• The chosen calculation slice executes deterministically and emits outputs, intermediate values, warnings and lineage.

• Reconciliation checks and approved golden tests pass within agreed tolerances.

• Results are searchable by run ID and show reporting date, dataset snapshot, rules, assumptions, engine version and status.

• All privileged actions and configuration changes are audited; server-side access checks are tested.

• AI features can be disabled without breaking ingestion or financial calculations.

Appendix A. Key entities and relationship summary
 • SourceSystem → SourceProfile → SourceContract → SchemaVersion / FieldMappingVersion.

 • ImportJob → ImportArtifact → ImportBatch → SourceRecord → CanonicalRecord; ValidationIssue and QuarantineItem reference
    relevant records/batches.

 • CanonicalRecord links to domain entities such as Instrument, Position, Counterparty, ContractualTerm, CashflowEvent,

1. Architecture and modelling principles
• Use a modular relational core (e.g. PostgreSQL) for metadata, entities, configurations, job states and results; use object storage for original files and large artifacts.

• Keep source payloads and canonical records distinct. A source file is evidence of what arrived; canonical records represent interpretation under a schema and mapping version.

• Use immutable versions for schemas, mappings, instrument terms, rules, assumption sets, module versions and report definitions.

• Every calculation run pins the exact dataset snapshot and all configuration/model versions. Historic run inputs are never updated in place.

• Use stable internal UUIDs plus source-scoped external IDs. Do not assume client identifiers are globally unique or immutable.

• Use fixed-precision decimal for authoritative financial values, not binary floating point. Store currency/unit and as-of/effective dates explicitly.

• Use typed columns for stable, frequently queried fields and governed extension attributes for genuinely variable source-specific fields.

• Separate calculation definitions/configuration from results; preserve evidence for independent reconciliation and explanation.

• Security, masking, retention, access control and audit are cross-cutting model requirements, not UI-only features.

2. High-level relationship map
source_system → source_profile/source_contract → import_job/import_artifact → source_record → field_mapping/mapping_version → canonical_record/instrument_version/position_version → calculation_run (pinned
inputs + rule_set + assumption_set + module_version) → intermediate_value and domain result tables → benchmark_result/report_instance. lineage_node/lineage_edge and audit_event preserve provenance and
governance.

• One logical schema has many immutable versions; each import and run references a specific version.

• One mapping definition has many versions; each import records the exact mapping version applied.

• One instrument has many immutable term versions and many positions over time.

• One rule definition has many versions; a rule set contains explicit rule versions and precedence.

• One calculation run has many input references, outputs, intermediate values, warnings and lineage edges.

• One scenario references a baseline and stores proposed changes separately; it never mutates baseline configuration.

• AI proposals are separate from approved rules/configuration. Approval and activation are explicit state transitions.

columns should be finalized after client data samples and domain conventions are confirmed.

5. Flexible source shape strategy
• Source adapters normalize transport/file details into import jobs and source records without assuming a fixed client schema.

• Until client samples arrive, use provisional source contracts and synthetic fixtures clearly labelled illustrative.

• Profile column names, observed types, null rates, uniqueness, ranges, date formats, currency patterns and distribution summaries.

• Mapping suggestions require human review and versioning before calculation use.

• Unknown fields are retained in protected artifact references or governed extension structures subject to classification and retention policy; never silently discard them.

• Schema drift creates a review event and impact report, not an automatic schema or financial-interpretation change.

6. Data lifecycle and change governance
 Step                            Required behaviour

 1. Register                     Create source profile and provisional/approved source contract; assign owner and classification.

 2. Receive                      Create import job, artifact metadata, checksum, batch and correlation ID; enforce file/security controls.

 3. Profile                      Inspect structure and quality; produce suggestions only, not schema mutations.

 4. Map                          Choose canonical schema and mapping versions; validate transforms and required fields.

 5. Validate                     Run schema/domain checks; create field-level issues/quarantine references; reconcile counts/totals.

 6. Canonicalize                 Create normalized records with source lineage and exact schema/mapping references.

 7. Configure                    Select approved assumptions, rule set and module version; isolate scenario changes from baseline.

 8. Calculate                    Create immutable run pinned to exact inputs/configuration; persist outputs, intermediate values and warnings.

 9. Verify                       Compare against approved benchmark cases at instrument/component/bucket/final metric levels.

 10. Review/publish              Apply authorization/approval policy; generate reports and audit consequential actions.

 11. Change                      Propose schema/mapping/rule change; assess dependencies, test, approve, activate and retain rollback reference.


7. Calculation reproducibility and lineage
• Each calculation_run references dataset_snapshot_id (or immutable input manifest), schema_version_id, mapping_version_id(s), rule_set/version, assumption_set_id, module_version_id and engine build/version.

• Persist start/end time, status, warnings, request/correlation ID and content hashes for important input/configuration manifests.

• Outputs carry metric code, value, unit/currency, dimensions, as-of date, run ID and lineage references.

• Trace final metric → component/bucket → intermediate values/rules → canonical records → source records/import artifact.

• Numerical tolerances are defined per metric by domain experts; no global tolerance is assumed.

• AI explanations read stored outputs and lineage; they never generate authoritative financial metrics.

8. Security and privacy controls
• Classify fields/artifacts and apply least privilege and tenant/portfolio/legal-entity scope where required.

• Keep identity-provider secrets and encryption keys outside application data; store only key references.

• Apply masking/redaction to logs, errors, AI retrieval, exports and UI according to approved policy.

• Audit schema/mapping/rule changes, approvals, calculation runs, exports and AI tool calls.

• Define retention/deletion for raw artifacts, derived records, AI requests and logs.

• Use synthetic data for demos unless client data use is explicitly approved; separate test and production environments.

• Enforce authorization server-side for data, lineage, reports and AI retrieval/tool calls.

12. Acceptance checklist
• Every entity has purpose, stable key, ownership, sensitivity classification and lifecycle.

• Source schema, canonical schema and mappings are separate, versioned objects.

• Unknown source fields can be profiled/reviewed without silently mutating the canonical schema.

• Historic instrument terms, rules, mappings and assumptions used by a run remain immutable and referenceable.

• Calculation output traces to source records and exact transformation/rule/engine versions.

• Authorization and audit are enforced server-side across data, calculations, reports and AI.

• Schema/rule changes have impact analysis, compatibility checks, regression evidence, approval and recovery path.

• Domain experts approve canonical fields, calculation specifications, benchmark cases and tolerance policy before results are represented as validated.
