                                    FINANCIAL RISK PLATFORM
                                             Five Synchronized Frontend / Backend Workstreams


 The project is organized into five paired workstreams. Each pair has a frontend implementation plan and a backend service/API plan. This
 index defines the common architecture and delivery sequence.
   The intended MVP is broad in platform coverage but lightweight in initial data volumes, integrations, UI/UX depth and
   domain-model completeness. It should demonstrate the architecture and a few representative end-to-end capabilities without
   pretending every financial module is production validated.

 Shared four-layer architecture
   Layer                                           Responsibility

   1. Universal Platform Foundation                Data ingestion, canonical schema and metadata, data quality, identity/access, audit, versioning
                                                   and change governance.

   2. Configurable Financial Domain                Instrument definitions, mappings, rule registry, assumptions, configuration lifecycle and
                                                   calculation-module contracts.

   3. Financial Calculation Modules                Liquidity/LCR/HQLA, cash-flow modelling, maturity ladder, and extension points for ALM/IRRBB,
                                                   collateral and capital.

   4. Intelligence and Experience                  Natural-language proposals, assistant, scenarios, lineage, explainability, agentic workflows and
                                                   evaluation.




 Five paired workstreams
   Pair            Scope                                              Why it exists

   WS1             Data Governance, Security & Platform               Establish a trustworthy, secure, versioned foundation across all financial
                   Foundation                                         modules.

   WS2             Data Ingestion, Mapping & Data Quality             Accept uncertain source shapes safely through configurable contracts,
                                                                      mappings and validation rather than hardcoding one client file format.

   WS3             Financial Domain Model & Calculation Services      Provide reusable financial-domain abstractions and a pluggable calculation
                                                                      service layer, then demonstrate breadth through bounded prototype modules.

   WS4             Risk Operations, Scenarios, Reconciliation &       Turn calculation services into a governed operational workflow with scenario
                   Reporting                                          comparison, traceability and evidence.

   WS5             AI/GenAI, Automation & Innovation Layer            Add differentiated intelligence while keeping data access, financial calculations
                                                                      and consequential actions governed.




 Recommended delivery order
 • Foundation controls are cross-cutting and begin first: agree canonical data principles, data classification, permissions, audit, schema
 versioning and change control.

 • Build the ingestion/mapping workbench against provisional synthetic source profiles because the client's real source shapes and attributes
 are not yet confirmed.

 • Implement the configurable financial framework and one bounded liquidity vertical slice; show other financial modules as registered
 extension points until requirements and benchmark cases are available.

 • Build run orchestration, scenarios, lineage and reconciliation as reusable services, not features hardcoded inside a single calculation.

 • Add AI/GenAI with bounded tasks, evidence grounding, permissions, evaluation and human approval; external APIs are optional, not a hard
 dependency.

 • Before production, complete client-specific data discovery, domain-expert validation, security testing, performance/resilience, migration and
 regulatory sign-off.



 Shared synchronization contract
 • Phase IDs P0–P6 and workstream IDs WS1–WS5 remain consistent across paired documents.

 • Feature IDs are paired across FE and BE and used in tickets, tests and release notes.




Financial Risk Platform | Workstream Index                                                                                                                Page 1
 • All proposed endpoint names must be confirmed in one OpenAPI specification before coding against them.

 • Unknown source attributes are a requirements uncertainty, not a reason to hardcode a guessed client schema. Use versioned mappings,
 configurable extensions, profiling and review.

 • Data security and governance are architecture-wide requirements, not an optional workstream that can be deferred.

 • Every financial result is reproducible from pinned data and configuration versions; no AI-generated result is authoritative.

                             FINANCIAL RISK PLATFORM
                                                   WS1 | Backend Development Plan
                                         Data Governance, Security & Platform Foundation




 Workstream objective: Establish a trustworthy, secure, versioned foundation across all financial modules.

 Product intent: A broad, lightweight, extensible platform foundation. Initial data volumes and module depth are limited deliberately;
 architecture, control points and expansion interfaces are not treated as throwaway demo code.
   Synchronization rule: This document is paired with the opposite-side document for the same workstream. Feature IDs, phase IDs,
   endpoint contracts, statuses and acceptance criteria must remain aligned.

 Shared architecture: Layer 1 Universal Platform Foundation → Layer 2 Configurable Financial Domain → Layer 3 Financial Calculation
 Modules → Layer 4 Intelligence and Experience. Data governance and security cross-cut all layers.




WS1 | Backend Plan                                                                                                                       Page 1
 1. Scope and Feature Coverage
  Feature ID         Feature                              Scope / implementation intent

  DG-01              Canonical schema and metadata        Define schema registry, version, owner, effective date, compatibility and lifecycle.

  DG-02              Identity and authorization           Enforce server-side roles/permissions and least privilege.

  DG-03              Data classification and protection   Classify fields, mask sensitive values, protect secrets and prevent sensitive logging.

  DG-04              Audit and provenance                 Record critical access/actions, actor, timestamp, resource and correlation ID.

  DG-05              Controlled model change              Review schema/mapping changes, assess downstream impact, test and approve before
                                                          release.

  DG-06              Environment and retention controls   Separate synthetic/test data from production; define retention, deletion and backup
                                                          assumptions.




 2. Phase-Wise Delivery
 P0 | Foundation contract
 Agree data/security assumptions, roles, classifications and architecture boundaries.

 P1 | Schema and metadata registry
 Versioned schemas, ownership, lifecycle and compatibility metadata.

 P2 | Security and audit controls
 Authentication integration, server-side authorization, audit records, masking and safe logging.

 P3 | Change governance
 Schema diff, compatibility checks, impact map, approval status and rollback/recovery plan.

 P4 | Cross-platform enforcement
 Connect other workstreams to shared identity, schema, audit and version services.

 P5 | Verification
 Test forbidden access, breaking schema changes, audit completeness and recovery paths.




WS1 | Backend Plan                                                                                                                                 Page 2
 3. Implementation Responsibilities
 Backend responsibilities
 • Define schema registry and immutable version records with lifecycle/status metadata.

 • Implement authorization middleware and permission checks on every protected endpoint.

 • Define field classification and masking policy; avoid sensitive payloads in logs.

 • Write append-oriented audit events for schema changes, approvals, exports and sensitive operations as required.

 • Implement schema diff, compatibility classification and dependency impact service.

 • Require approval for breaking changes and preserve a recovery path; never silently reinterpret historic records.

 4. Paired API / Feature Contract Matrix
 Endpoint names are proposed contracts for alignment, not a claim that the APIs already exist. Confirm payload schemas in the shared
 OpenAPI contract before implementation.

  Shared feature pair            Capability                     Proposed API contract

  FE-DG-01 / BE-DG-01            Schema catalogue/version       GET /api/v1/schemas; GET /api/v1/schemas/{schema_id}/versions; GET
                                 compare                        /api/v1/schemas/{schema_id}/diff

  FE-DG-02 / BE-DG-02            Permissions                    GET /api/v1/me/permissions; authorization enforced on protected APIs

  FE-DG-03 / BE-DG-03            Audit timeline                 GET /api/v1/audit-events?resource_id={id}

  FE-DG-04 / BE-DG-04            Change review                  POST /api/v1/schema-change-proposals; GET /api/v1/schema-change-proposals/{id};
                                                                POST /api/v1/schema-change-proposals/{id}/impact-analysis; POST
                                                                /api/v1/schema-change-proposals/{id}/approval




 5. Cross-Cutting Rules
 • The canonical model and source mapping are versioned separately. Unknown source attributes are preserved or quarantined by explicit
 policy, not silently discarded.

 • Every calculation run must bind dataset snapshot, schema/mapping version, rule-set version and calculation-engine version.

 • Server-side authorization is authoritative. The frontend may hide unavailable actions but does not enforce security.

 • No AI-generated code is executed. AI output is validated against schemas and policy, and consequential actions require authorized approval.

 • All errors use a structured response with code, message, details and correlation_id. Sensitive payloads and secrets must not be logged.

 • Prototype financial modules use synthetic/approved data, documented assumptions and test fixtures; do not claim regulatory certification or
 Moody's parity.

 • The platform is designed for breadth, but production-grade depth is not implied for every financial domain. ALM/IRRBB, collateral, capital, live
 market data and regulatory feeds require their own specifications and validation.

 6. Definition of Done
 • Every feature ID in this document has a matching feature ID in its paired frontend/backend document and in the shared feature register.

 • Each endpoint has request/response schemas, status enums, authorization expectations and error examples in OpenAPI.

 • Frontend components use actual API responses or clearly labelled mocks matching the contract.

 • Backend tests cover validation, permissions, version binding and domain logic appropriate to this workstream.

 • The cross-workstream integration test passes for the features included in the release.


   Change-control rule: Any change to endpoint, field name, enum, versioning behaviour or acceptance criteria must be reflected in
   both paired documents and the shared contract in the same change.

 P5 | Adapter readiness
 Document and test adapter contract for future warehouse/API/event source integrations.
